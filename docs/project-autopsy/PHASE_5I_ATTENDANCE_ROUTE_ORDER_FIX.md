## Previous Route-Order Risk Summary

Phase 5H found that the unprefixed attendance resource route was registered before more specific attendance routes. Because `Route::resource('attendance', AttendanceController::class)` registers `GET /attendance/{attendance}`, static and specific routes registered after it could be swallowed by `AttendanceController@show`.

The affected unprefixed routes were:

- `GET /attendance/bulk-mark`
- `GET /attendance/student/{studentId}/report`

This meant `/attendance/bulk-mark` could resolve as a resource `show` request with `attendance = bulk-mark` instead of dispatching to `AttendanceController@bulkMark`.

## New Route Order

The unprefixed attendance route cluster now registers all custom static/specific routes before the resource route:

```php
Route::get('/attendance/reports', [AttendanceController::class, 'reports'])->name('attendance.reports');
Route::get('/attendance/export', [AttendanceController::class, 'export'])->name('attendance.export');
Route::get('/attendance/bulk-mark', [AttendanceController::class, 'bulkMark'])->name('attendance.bulk-mark');
Route::get('/attendance/student/{studentId}/report', [AttendanceController::class, 'studentReport'])->name('attendance.student.report');
Route::resource('attendance', AttendanceController::class)->except(['reports', 'export']);
```

## Remaining Risks

1. API `bulkMark()` remains an unguarded bulk write path.
2. API `bulkMark()` still uses raw bulk insert behavior according to Phase 5H.
3. API `bulkMark()` still lacks preflight enforcement.
4. API `bulkMark()` still lacks terminal/inactive student exclusion.
5. API `bulkMark()` still lacks a duplicate pre-check and transaction.
6. API `store()` still has marked-by trust/spoofing risk according to Phase 5H.
7. Legacy class string usage remains in attendance flows.
8. Safe transactional bulk apply has not yet been designed.
9. Existing attendance data may still contain duplicate or legacy-class rows from earlier behavior.
10. Admin and API attendance write paths still need a unified canonical write policy.

## Recommended Phase 5J Next Step

Phase 5J should guard API `bulkMark()` with a controlled disabled response until a safe API preflight/apply design exists.

Recommended first API behavior:

- Return a clear `409 Conflict` or `423 Locked` response from API `bulkMark()`.
- Do not perform raw `Attendance::insert()`.
- Do not add an API apply token yet.
- Leave API single-record behavior unchanged until the bulk bypass is closed.

This is the smallest next safety step because the web route collision is now fixed, while API `bulkMark()` remains the highest-risk unguarded bulk attendance write path.
