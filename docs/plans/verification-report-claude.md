## PART 2 — FRESH FINDINGS (independent review, not limited to the claims)

### CRITICAL

1. **Root-cause data-integrity bug: two `school_classes` rows soft-deleted while holding 98 live students.** Migration `2026_07_23_100000_merge_class_management_into_school_classes.php` (lines 76-83) soft-deletes `school_classes` IDs 22 (`"Class 11"`, no stream) and 23 (`"Class 12"`, no stream) as "confirmed dead" duplicates, in favor of the stream-specific rows (IDs 14-19: `Class 11/12 Science/Commerce/Arts`). Live DB verification shows the opposite is true: **id=22 has 65 currently-enrolled students, id=23 has 33** (98 total), while every one of IDs 14-19 has **zero** students. Because `SchoolClass` uses `SoftDeletes`, Eloquent's default scope hides 22/23 from normal queries — `$student->schoolClass` silently resolves to `null` for these 98 students. **Confirmed downstream damage:**
   - `Admin/AdmitCardController.php:58` and `Admin/ExamArrangementController.php:76,99` both do `Student::where('class', $exam->class_name)`. Live check: `Exam::first()->class_name` = `"Class 10"`, but `Student::where('class','Class 10')->count()` = **0** — every exam's admit-card generation and seating arrangement silently returns zero students, for every class, due to the format mismatch between the frozen `class` string and `school_classes.name`.
   - `app/Exports/UdiseStudentsExport.php:52` falls back to the stale `class` string for these 98 students, producing inconsistent labels (`"Class 11"` / `"XI"` / `"XI-"`) in a government compliance export.
   - `FeeCollectionController.php` (multiple lines) falls back to the same stale string for fee receipts/statements for these 98 students.
   - **Described fix (not applied):** restore `school_classes` 22/23 (un-soft-delete), or write a follow-up migration that reassigns the 98 affected students' `school_class_id` to the correct stream-specific row (14-19) based on actual stream data, then re-verify before considering 22/23 safe to retire. Re-run the A2 reconciliation that produced the original (incorrect) "confirmed dead" determination.

2. **`academic_events` migration not applied to the working dev database**, meaning the D2 holiday-block guard throws an uncaught `QueryException` on every attendance-marking attempt right now (both web and API), rather than gracefully skipping or blocking. See D1/D2 above. **Described fix (not applied):** run the pending migration in this environment (or confirm which environment is authoritative and align it), and consider wrapping the `AcademicEvent::isHoliday()` calls in `AttendanceController` in defensive error handling similar to the dashboard's pattern, so a missing/failing calendar table degrades rather than breaks attendance marking.

3. **Broad authorization gaps across the academic/finance-adjacent admin surface** — not all introduced by this rebuild, but all in-scope and unaddressed by it. Controllers with **zero** `authorize()`/role-middleware/`hasRole()` check on write actions:
   - `ClassTeacherAssignmentController` (create/update/delete class-teacher assignments)
   - `Admin\TeacherClassAssignmentController`
   - `Admin\TeacherSubjectAssignmentController`
   - `Admin\StudentPromotionController` (bulk `school_class_id`/fee-structure mutation — the single most consequential unguarded write in the module; see C2)
   - `Admin\HomeworkNoticeController` (write actions only — `index`/`show` are guarded)
   - `Admin\CertificateTemplateController`
   - `Admin\CertificateController` (`store`/`update`/`destroy`/`approve`/`publish`/`lock`/`revoke`/`downloadPdf` — `publish()` can null a student's class/section and mark them TC-issued with zero role check; the `downloadPdf()` gap was newly added by this rebuild, self-acknowledged in its own comment)
   - `Admin\TeacherAttendanceController` (reachable write actions: `store`, `markAllPresent`, `updateAttendance`)
   - `Admin\SyllabusController` (a `SyllabusPolicy` is registered but never invoked from the controller)
   - The base `AttendanceController` — and the non-admin `attendance/*` routes (`routes/web.php` ~195-205) carry **only `web` middleware, no `auth` at all**, meaning attendance can be marked/updated/deleted while **logged out**.

   This is systemic: the entire `admin/*` route group (`routes/web.php:473`) has no role middleware, unlike sibling groups (e.g. `role:accountant` at line 591), so protection depends entirely on each controller remembering to call `authorize()` — and roughly a third of the academic-domain controllers don't. **Described fix (not applied):** add role/permission middleware at the route-group level as defense-in-depth, and add missing policies + `authorize()` calls to each controller listed above, prioritizing `StudentPromotionController`, `CertificateController`, and the unauthenticated `attendance/*` routes first.

### HIGH

4. **Two acknowledged-broken routes left in place instead of removed or fixed** (B9, B10 above): `bell-timing/bulk-create` → nonexistent `processBulkCreate`, and `Admin\HomeworkController`'s 5 unimplemented resource actions. Both throw fatal errors if hit. **Described fix:** either implement the missing methods or delete the dead routes/controller, consistent with how the rest of the B-group demolition was done.
5. **`UdiseStudentsExport` produces incorrect data** for the 98 students affected by finding #1 — a concrete, demonstrable regression flowing from the class-merge migration into a government compliance artifact.
6. **Admit card and exam-seating generation silently return zero students for every exam**, not just the 98 affected by finding #1 — the `class` string vs. `exam.class_name` format mismatch (`"1"` vs `"Class 10"` etc.) affects the entire student body, since these two readers never used `school_class_id` at all. This predates the rebuild but is squarely a "regression risk on deprecated column readers" item the rebuild was supposed to catch and didn't.

### MEDIUM

7. **`TimetableSlotPolicy::create()`/`update()`** grant write access to **any** teacher for **every** class's timetable, not just their own — a scoping gap rather than a missing check.
8. **`CertificateController::store()`** leaks raw exception text to the end user via `withErrors(['error' => 'Failed to create certificate: ' . $e->getMessage()])` — minor information disclosure.
9. **Destructive migrations without a backup step:** `2026_07_23_100100_drop_bare_classes_table.php` and `2026_07_23_100200_drop_dead_attendance_tables.php` both have well-formed schema-only `down()` methods, but neither has a data-preservation step before the drop — any data present at drop time (comments claim there was none, not independently re-verified beyond the comment) would be unrecoverable on rollback.

### LOW

## PART 4 — VERDICT

### Health score: **4.5 / 10**

### Assessment

The rebuild delivered real, verifiable work — the dead-code demolition (group B) is mostly genuine (7 of 10 items fully verified gone), the test suite is exactly at its claimed baseline with zero new regressions across 1151 tests, and several new features (academic calendar CRUD, compliance fields, certificate PDF, consent-field mass-assignment protection) are code-complete with real passing feature tests, not just self-reported claims. That said, this audit surfaced one severe, currently-live data-integrity bug — 98 enrolled students silently orphaned from their class record by an incorrect migration premise, with confirmed downstream breakage in admit cards, exam seating, and the UDISE compliance export — plus a migration that never made it into this working database, which means the flagship holiday-attendance feature currently crashes instead of working. On top of that, two of the specific security/reliability claims this rebuild made about itself (StudentPromotionController's authorization and idempotency guard; the attendance parent-notification pipeline) are simply false — the code doesn't do what the rebuild said it does — and the fresh-eyes authorization sweep found that roughly a third of the academic-domain admin controllers, including the highest-stakes ones (bulk student promotion, certificate publishing/revocation, unauthenticated attendance marking), have no access control beyond being logged in. The class-consolidation goal itself (group A) is also incomplete: `class_management` was never retired despite a live, currently-reachable code path against it. This is a partially-successful rebuild with good bones (clean migrations mechanically, solid test discipline, genuine feature completeness where it was actually finished) undermined by an unverified data-migration assumption and a pattern of claiming security/completeness that a closer read doesn't support.

### Top 5 recommended next actions (priority order)

1. **Fix the school_classes 22/23 data bug immediately** — this is live, silently corrupting admit cards, exam seating, fee displays, and the UDISE export for 98 real students today. Restore the rows or properly re-point their students, then re-verify before any further "retirement" of legacy class data.
2. **Run the pending `academic_events` migration in this dev environment** (or confirm/align on the authoritative environment) — the holiday-attendance guard currently throws a fatal error on every attendance mark attempt against this database.
3. **Add authorization to the ~9 unguarded write controllers**, prioritizing `StudentPromotionController`, `CertificateController`/`CertificateTemplateController`, and the unauthenticated `attendance/*` routes (currently reachable while logged out) — these are the highest-consequence gaps found.
4. **Either implement or delete the two acknowledged-broken routes** (`bell-timing/bulk-create`, `Admin\HomeworkController`'s missing CRUD methods) rather than leaving them half-wired to fatal errors.
5. **Correct the rebuild's own record of what's done**: the promotion double-submit guard and the attendance parent-notification pipeline do not exist as claimed — either build them for real or update whatever tracking/status docs asserted they were complete, so the next person (human or AI) doesn't inherit the same false premise this audit had to catch.
